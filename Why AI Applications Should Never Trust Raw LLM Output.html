Why AI Applications Should Never Trust Raw LLM Output

Akshat GuptaUpdated October 2026~12 min readIntermediate
PythonPydanticFastAPILLM APIsSecurity

Example implementationThis is a teaching essay with example code. It does not describe a production deployment.

1. The core mistake

Developers often treat an LLM call like a function call: send input, get a result, use it. But a function has a contract. An LLM has a tendency. Most of the time the reply matches what you asked for, and that is exactly what makes it dangerous: the failures are rare enough to ship past testing and common enough to hit users.

The rule is simple: model output is untrusted input, in the same category as a form field typed by a stranger. You would not put that straight into a SQL query, and you should not put model output straight into your logic either.

2. Seven ways raw output fails

FailureExample
Malformed structureJSON wrapped in markdown fences, trailing commentary, truncated mid-object
Wrong types"age": "thirty-two" instead of a number
Missing fieldsA required key is simply absent
Extra fieldsUnrequested keys such as is_superuser
Out-of-range valuesA role or status that is not in your enum
Plausible but wrongValid shape, invented or misread value
Manipulated outputText steered by hostile content in the input (prompt injection)

3. Build a validation boundary

LLM text→parse JSON→validate schema→business rules→application

Nothing before the validator is allowed to touch your database, your API response or your tools. In Python, Pydantic is the natural tool:

python · boundary.pyexample
import json
from typing import Literal, Optional
from pydantic import BaseModel, ConfigDict, Field, ValidationError


class UserDraft(BaseModel):
    model_config = ConfigDict(extra="forbid")  # reject invented fields

    name: str = Field(min_length=1)
    age: int = Field(ge=0, le=120)
    role: Literal["viewer", "editor"]
    email: Optional[str] = Field(default=None, pattern=r"^[^@\s]+@[^@\s]+$")


class UntrustedOutput(Exception):
    pass


def parse_user(text: str) -> UserDraft:
    try:
        return UserDraft.model_validate(json.loads(text))
    except (json.JSONDecodeError, ValidationError) as exc:
        raise UntrustedOutput(str(exc)) from exc

extra="forbid" matters: by default Pydantic ignores unknown fields, which hides the model inventing keys. Forbidding them makes the invention visible.

4. Schema-valid is not true

Validation proves the shape is right. It cannot prove the value is correct: a model can return "age": 34 when the document says 43, and every check passes. So add layers beyond the schema:

  • Business rules: dates not in the future, totals that equal the sum of line items, IDs that exist in your database.
  • Grounding checks: for extraction, confirm that the value actually appears in the source text.
  • Human review: for high-stakes data, treat output as a draft a person confirms.

Do not claim more than you checkedNever present a model-extracted value as verified just because it passed the schema.

5. Repair and retry, with limits

When validation fails, one reasonable response is to send the error back to the model and ask for a corrected reply. Keep it bounded and keep failing closed:

python · retry.pyexample
MAX_TRIES = 2


async def get_user(prompt: str) -> UserDraft:
    messages = [{"role": "user", "content": prompt}]
    for attempt in range(MAX_TRIES + 1):
        text = await call_llm(messages)  # your provider wrapper
        try:
            return parse_user(text)
        except UntrustedOutput as exc:
            messages += [
                {"role": "assistant", "content": text},
                {"role": "user", "content": f"Invalid: {exc}. Return only corrected JSON."},
            ]
    raise UntrustedOutput("model failed validation after retries")

Retries cost time and money, and a model can fail the same way repeatedly, so cap the attempts and have a defined behavior when they run out: return an error, queue for review, or fall back to manual entry.

6. Structured output features are not a substitute

Many providers offer JSON modes or schema-constrained decoding, which reduce malformed output and are worth using where available. They improve the odds; they do not remove the need to validate. Support and strictness differ between providers and models, constrained output still cannot guarantee that values are true, and your own business rules live outside any provider feature. Use them as a first line of defense, with your own validation behind it.

7. Output that triggers actions

The risk grows when output is not just stored but acted on. If a model's text becomes a database query, HTML, a shell command or a tool call, then whoever can influence the model's input can influence that action. Prompt injection is exactly this: instructions hidden in a document, web page or email that the model then obeys.

  • SQL: use parameterized queries; never build SQL strings from model text.
  • HTML: escape output before rendering it in a page.
  • Tool calls: keep an allow-list of tools and validate every argument like user input.
  • Shell and file paths: avoid passing model output to them; if unavoidable, restrict to fixed choices.
  • Least privilege: the credentials behind an AI feature should only be able to do what that feature needs.
python · allowlist.pyexample
ALLOWED_TOOLS = {"search_orders", "get_invoice"}  # nothing else, ever


def run_tool(name: str, args: dict):
    if name not in ALLOWED_TOOLS:
        raise PermissionError(f"tool not allowed: {name}")
    # validate args with a per-tool Pydantic model, then execute
    ...

8. Fail safe, not silent

Decide in advance what happens when output is invalid. The worst choice is quietly using a default that looks like real data. Prefer an explicit error, a flag for human review, or a clearly marked "unknown". Log failures, because the validation-failure rate is one of the few honest quality signals you have.

PrivacyDo not log full prompts or outputs that contain personal data. Log error types and field names instead.

9. Testing the boundary

Test the validator with bad outputs on purpose. This needs no model and no network:

python · test_boundary.pyexample
import pytest

BAD = [
    "not json at all",
    '{"name": "A", "age": "thirty", "role": "viewer"}',
    '{"name": "A", "age": 30, "role": "admin"}',
    '{"name": "A", "age": 30, "role": "viewer", "is_superuser": true}',
    '{"age": 30, "role": "viewer"}',
]


@pytest.mark.parametrize("text", BAD)
def test_rejects_bad_output(text):
    with pytest.raises(UntrustedOutput):
        parse_user(text)

Beyond that, build a small evaluation set from your own real inputs and measure how often outputs are correct, not just valid. Do not borrow a number from a vendor announcement.

10. Checklist

  • Treat model output as untrusted input.
  • Parse, then validate against a strict schema (forbid extras).
  • Add business-rule and grounding checks for values that matter.
  • Bound retries and fail closed.
  • Allow-list tools; parameterize queries; escape output.
  • Give AI features least-privilege access.
  • Test the validator with deliberately bad outputs.
  • Keep a human in the loop for high-stakes decisions.

11. Conclusion

An LLM is a useful component with an unusual contract: it is often right and never guaranteed. Put a boundary around it, and let only validated, checked, permissioned data cross into the rest of your system. Back to portfolio →
